* [Mobile UX research: reader gesture and navigation patterns](/findings/01M7AQ6AP482MPSCXEV5DH2P8D.md) - Web research (2026-11-13; sources are mostly reviews and blogs, verify against Apple HIG, Material and WCAG before relying on specifics). Reader apps converge on: swipe on a list row to mark read (right) and save/star (left), configurable per side (Reeder, Unread); long-press on a row opens a menu (save, share, mark read); Reeder 3 two-finger swipe marks items above or below as read; Reeder 5 mark-as-read-on-scroll exists but is OFF by default; Unread uses a tug gesture to move between articles; Reeder 2 used edge swipes for back/forward; NetNewsWire uses toolbar buttons instead of gestures: a filter button, and mark-all-as-read at the bottom with an optional confirmation. Accessibility: every gesture needs a visible alternative (buttons or a menu), swipe-only excludes screen reader and motor-impaired users; pull to refresh is expected in feeds but needs a visible refresh button too; use consistent gestures across the app. Touch: 44x44 px minimum (Apple) / 48 px (Google), WCAG 2.5.8 minimum is 24x24 CSS px with spacing, keep at least 8 px between targets. Layout: use env(safe-area-inset-*) with viewport-fit=cover for notch and home indicator, 100dvh instead of 100vh, bottom navigation for 3-5 destinations is the dominant pattern but the thumb-zone claims are contested and hamburger menus sit in the hard-to-reach area; primary actions in the central/bottom area. Reading: readability first, no hard evidence found on line length; platform guides require text scaling support (Dynamic Type on iOS). Sources: matthewcassinelli.com/reeder-4, macsparky.com/blog/2021/03/why-im-switching-to-reeder-5, macstories.net/news/unread-1-2-adds-image-viewer-new-gestures-and-more, brooksreview.net/2012/06/reeder-3, blog.logrocket.com/ux-design/accessible-swipe-contextual-action-triggers, bitsofco.de/tips-for-making-interactive-elements-accessible-on-mobile-devices, smashingmagazine.com/2020/02/design-mobile-apps-one-hand-usage, addyosmani.com/blog/touch-friendly-design. Current app state (code check): h-dvh shell, mobile sidebar as a Sheet, header search icon, stacked list to article with history-aware back link; MISSING: safe-area insets and viewport-fit=cover, any touch or swipe handling, overscroll-behavior (pull-down in the installed PWA can reload the whole page), touch-target audit (list icons are size-2 and size-3.5), prev/next controls in the reader.
* [Edge-swipe navigation in installed PWAs (iOS and Android)](/findings/01M7AQD717QC4E439E39QM6P7Y.md) - iOS standalone PWA: edge swipe back is a system gesture with no official opt-out; overscroll-behavior-x:none prevents the navigation redirect in some versions but not the swipe animation; a touchstart preventDefault guard near the left/right edge is reported to work only partially and loses to native handling while scrolling. Android: system gesture navigation is OS-level; Chrome's in-page overscroll history navigation (touchpad and edge) is controlled with overscroll-behavior-x. Sources are forum posts and Chrome/MDN docs (developer.chrome.com/blog/overscroll-behavior, developer.mozilla.org/docs/Web/CSS/overscroll-behavior-x, forum.ionicframework.com swipe back gesture on iOS PWA thread); verify on real devices before relying on any of it.
