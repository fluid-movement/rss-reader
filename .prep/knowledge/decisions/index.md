# decisions

## Entries

* [No public sign-up; users created via console; passkeys](/decisions/01M7A3TWQGX6E3JH8E286BHKZC.md) - There is no sign-up page or endpoint. Users are created only with a console command. Sign-in is email+password plus passkey (WebAuthn) via Better Auth. Reason: self-hosted, single-person app exposed publicly on Coolify.
* [In-process refresh timer, manually triggerable](/decisions/01M7A3TWS2SA5QF150AFJ2P4Y8.md) - Feeds refresh from an in-process interval timer in the server, plus manual refresh of one feed or all. No external cron. Reason: single Coolify container, simplest option.
* [No offline support or extra integrations in v1](/decisions/01M7A3TWTQQKX8ZNA17MF254CV.md) - v1 is an online-only PWA (installable, app shell cached, data fetched live). No offline article caching, Fever/Google Reader API, push notifications or in-app social sharing. Only a share-link button for article URLs. Reason: keep it simple; offline can be v2.
* [Three-pane layout, Readability extraction, FTS5 search](/decisions/01M7A3TWWCRKT1SNF96RKW8212.md) - Desktop is three panes (sidebar/list/reader), mobile stacked. Full-text extraction uses Readability. Search uses SQLite FTS5. UI uses shadcn-svelte components only.
* [Use better-sqlite3 with Drizzle, not node:sqlite](/decisions/01M7A44AKKCXM9N7TX3Q9EXPDC.md) - Installed drizzle-orm 0.45.2 has no node-sqlite driver (only in 1.0 betas), so the DB uses drizzle-orm/better-sqlite3. Stable, FTS5 built in. Reason: scaffold imported a non-existent driver and caused 500s.
* [Committed drizzle migrations applied at boot; per-worktree SQLite](/decisions/01M7A5RGRVRM8Z1E8NSY3N42KB.md) - Schema changes use drizzle-kit generate with migrations committed under drizzle/ and applied at server start (init() in hooks), never db:push. Parallel worktrees each use their own relative DATABASE_URL (local.db) and dev port so SQLite files never collide. The /feeds management page belongs to the feed-subscribe issue; the sidebar only links to it.
* [Deploy as single Node container, ORIGIN env only](/decisions/01M7A62RBVV6P1CRSAPD8FDFDK.md) - Image is node:24-bookworm-slim multi-stage, non-root, SQLite on /data volume, single replica, CMD node build. Behind Coolify's proxy ORIGIN set to the public https URL is sufficient (no PROTOCOL_HEADER/HOST_HEADER). Retention is a per-user DB setting, not an env var. Image build is still unverified (Docker daemon was down).
* [safeFetch decodes compression with decompressed size cap; HTML sanitized at ingest and render](/decisions/01M7A79HP18TJZR0VER8DKN1AJ.md) - safeFetch sends Accept-Encoding gzip/deflate/br and decodes via node:zlib with the size cap enforced on decompressed bytes (rejecting compressed responses breaks real feeds that ignore identity). Content is sanitized when parsed/ingested (relative URLs resolved against item link, rel noopener) and again at render time in the reader. Fetches are pinned to the validated IP (SSRF). Reason: found in review of the feed subscribe issue.
* [OPML import inserts feeds without fetching; UI lives on /feeds until settings exists](/decisions/01M7A79HQRA3YKPAJ9HJHTW21Y.md) - OPML import creates feeds with next_fetch_at=now and lets the scheduler fetch them, so large imports are instant. The import/export panel is mounted on the /feeds page; the later settings issue may move it. Reason: avoid blocking requests and avoid parallel-issue conflicts on a not-yet-built settings page.
* [Scheduler: safe last_error, manual refresh cooldown with feedback, 30 min default](/decisions/01M7A8PZJH36WHT1PVAR4P42BN.md) - last_error stores messages only from FeedFetchError/FeedParseError (truncated), anything else becomes a generic message and is logged server-side. Manual refresh has a 30s per-feed cooldown that reports 'skipped' instead of pretending success. Default refresh interval is a shared DEFAULT_REFRESH_MINUTES=30 used by both subscribe and OPML queueing. Reason: review findings on the refresh scheduler issue.
* [Seed script may hold the dev credentials but must refuse non-local runs](/decisions/01M7A8PZMHVPCAQG1QA2P91MEJ.md) - The user allowed committing the throwaway dev account (same as the justfile create-user recipe) in the seed script. It must exit before touching the DB when NODE_ENV is production or ORIGIN is not localhost, because the public Coolify deployment has no sign-up and a known-password account there would be a backdoor. Reason: user stated it is not personal data; guard makes it safe to publish.
* [Reader state mutations use a JSON endpoint with optimistic client state](/decisions/01M7A9QAK9D9KD6RFBVT3SZ7YB.md) - Read/star/mark-read mutations go through POST /api/state (session required, same-origin check, JSON content type, validation, 404 on unowned ids) with optimistic overrides in reader-state.svelte.ts, rollback plus toast on failure, and refetch on focus/visibility plus a 60s poll. Reason: simplest way to get instant optimistic updates and cross-device sync; reviewed in a real browser.
* [Desktop layout uses fixed pane widths, not resizable panes](/decisions/01M7A9QANAZ3VRMBVM6EDHR7MK.md) - The implementer replaced the draggable resizable panes with CSS fixed widths (sidebar w-72, fixed list column) and CSS-only responsive switching, which removed the SSR layout flash. A browser review judged it acceptable for the simple clean design; it is cramped at about 1024px, tracked in the list follow-up issue. Restore resizing later only if wanted. Refines the three-pane decision.
* [Views host the list in a layout; lists are capped with Load more; sync invalidates narrow keys](/decisions/01M7AB1NE912NXF9NTE7PJD6BJ.md) - Each view (all, unread, starred, feed, folder) has a +layout that hosts the list so it persists when an item opens (item is a nested page); lists load the 100 newest with cursor-based Load more via GET /api/articles and the open item is always merged in; sync (focus, visibility, 60s poll) invalidates app:list, app:item and app:feeds instead of invalidateAll and refetches extra pages in chunks of 100. /api/state caps bodies at 4096 bytes. New views such as search should reuse this layout pattern. Reason: scroll position and cost at scale, verified in a real browser.
* [Full-text extraction must not parse HTML on the main thread unbounded](/decisions/01M7AB1NFZ6JCXQ46D0PECVX0P.md) - Review measured linkedom plus Readability freezing the server for over a minute on a 49 KB page of deeply nested divs; the fetch timeout cannot interrupt synchronous parsing. Extraction therefore must parse in a terminable worker thread (or equivalent) with a hard timeout, plus cheap pre-rejection by tag count and nesting depth and a lower byte cap, and must work in vite dev, vitest, node build and the Docker runtime image.
* [Extraction parses in an eval worker thread, not a bundled worker file](/decisions/01M7ABPYQ9MZ9NSA2C1VYAHVEV.md) - dom-worker.ts creates short-lived worker threads with {eval:true} from inline CommonJS that loads linkedom and @mozilla/readability via createRequire(import.meta.url), because bundled worker file URLs are unreliable across vite dev, vitest, node build and the Docker runtime (prod node_modules, no src/). Limits: 5s terminate, 256 MB old-gen, max 2 workers with a queue, pre-scan (50k tags, depth 150), 1 MiB page cap. Verified in node build from another cwd with no src/.
* [Seed uses real feeds pulled by the app, not fake data](/decisions/01M7ACNV4AK2AWEKXPFSPP431S.md) - User decision: a seed with fabricated feeds and items veils real problems. The seed creates the dev user and folders and queues real popular feeds (verified live 2026-11-13, covering RSS, Atom, RSS 1.0, JSON Feed, gzip/br, redirects, a wrong content type, large feeds and one dead URL); the running app's scheduler pulls them. The script itself stays network-free and keeps the production guard. Supersedes the seed issue's fake-fixture design; the guard decision still applies.
* [Search index is trigger-synced FTS5 using an app-defined SQL function; only app connections may write items](/decisions/01M7ACP9XWR54E4KDYJT01M463.md) - items_fts is kept in sync by triggers that call item_search_text/item_clean_title, SQL functions registered in connectDatabase(). Every writer must use connectDatabase (app boot, seed, create-user, scheduler). drizzle-kit migrate, push and studio cannot write items (no such function) so db:migrate and db:push refuse with a message; app-boot migration is the supported path, db:generate stays fine. search-text.ts lives in src/lib/server/db/ so the Docker runtime image (which copies that folder) can run user:create. Reason: automatic re-index of any items UPDATE including extraction's full_content.
* [Retention prunes only read, unstarred items and leaves tombstones](/decisions/01M7ACP9ZPJG9SHGB5BNZS79D6.md) - Daily job (2 min after start, then every 24 h) deletes items the owner has read, not starred, older than user_settings.retention_days (default 30, <=0 keeps all), in transactions of 200 with yields. A pruned_items(feed_id, guid) tombstone written in the same transaction makes ingestItemIds treat them as already seen so pruned items still present in their feed never return as unread or get re-extracted. Items without an item_state row (never opened) are unread and are never deleted. Lowering retention later cannot restore pruned items; tombstones are tiny and cascade with their feed.
