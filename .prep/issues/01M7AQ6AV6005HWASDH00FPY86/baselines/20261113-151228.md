In the article view on a phone, swipe horizontally to move between articles: swipe LEFT = next article, swipe RIGHT = previous (user decision; standard paging). Next/previous follow the order of the list the user came from (the current view including its Load more pages; at the end of loaded items fetch the next page first). Behavior: the article follows the finger with a short slide/peek transition, commits past a distance or velocity threshold, otherwise snaps back; reduced-motion users get an instant switch; the first/last article gives a small rubber-band and no navigation. No conflicts: vertical scrolling (axis lock), horizontally scrollable content (tables, code blocks, wide images, embedded players: a gesture that starts inside such an element belongs to that element), image zoom later, text selection, and the system edge-swipe back gestures (use the shared edge-guard helper from the foundations issue: touches starting within about 24-28 px of either edge are ignored; Back always returns to the list with scroll position preserved). Visible alternatives: previous/next controls and a position indicator ('12 of 100') in the reader toolbar (the full bottom action bar is a separate issue); keyboard j/k keeps working and stays in sync. Navigation uses the existing item routes (URL changes per article, history replaceState so the browser Back button still returns to the list in one step, not through every article), mark-read-on-open semantics stay, optimistic state and narrow invalidation stay, preload the neighbor article data on touch start/idle.
